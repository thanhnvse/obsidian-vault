# A cache stampede happens when a hot key expires and many requests regenerate it at once

## Core idea
When a frequently accessed cache item expires, every request that arrives before it is rebuilt sees
a miss and regenerates the same item at the same time; this is a cache stampede. Its size grows with
both the request rate and the time one rebuild takes: an item read 10 times per second that takes
3 seconds to rebuild is regenerated by 30 requests. The concurrent rebuilds slow each other down, so
the stampede can cascade into overloading the database the cache was protecting. Mitigations
therefore aim to let one request, or a few, rebuild the item instead of all of them.

## Why choose / why not
- Choose a per-key lock when: a few hot keys are expensive to rebuild; the request that gets the
  lock rebuilds, while the others wait or serve the stale copy.
- Choose probabilistic early expiration when: the lock's extra write is unwanted and a value may be
  refreshed a little before it expires; not for values that must not be rebuilt early, such as
  hourly statistics.
- Don't add either when: keys are cold or cheap to rebuild; a few duplicate misses cost less than
  the extra machinery.

## Interview angle
- Probed as "the hit rate is 99% but the database spikes on the hour"; the common wrong answer is
  "make the TTL longer", which moves the stampede instead of removing it.
- Strong answer: tell one hot key expiring (lock or early refresh) apart from many keys expiring
  together after a bulk load (random jitter on each TTL).
- Java detail: Caffeine 3.3 `Cache.get(key, mappingFunction)` applies the function at most once per
  key, but only inside one JVM, so 20 instances can still send up to 20 rebuilds.
